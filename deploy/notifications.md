# 알림 연동 및 운영

- 한국 시간 09:00에 당일 마감 항목을 개별 발송하고, 18:00에 D-1~3 묶음과 신규 묶음을 각각 최대 한 건 발송한다. 미완료 항목만 대상으로 한다.
- 마감 알림은 해당 정시보다 먼저 사용자에게 연결된 항목만 대상으로 한다. 5분 재시도에서도 같은 등록 시각 경계를 사용하므로 정시 이후 등록된 항목을 지난 슬롯에 추가하지 않는다. 정시에 정확히 등록된 항목도 해당 슬롯에서는 제외한다.
- 신규 기준은 사용자에게 처음 연결된 `UserTodoStatus.createdAt`이다. 전날 18:00 이상, 당일 18:00 미만을 조회한다. 감사 시각은 JVM 로컬 시간이므로 조회 경계를 같은 시간대로 변환한다. 마감 시각은 한국 로컬 시간이다.
- 묶음 대표는 마감 시각, 할 일 ID 오름차순으로 고른다. 신규와 마감 임박에 동시에 해당하면 각각 발송한다.
- 시스템 알림 OFF이면 네 종류 모두 발송하지 않는다. 기존 `notificationThresholdMinutes`, `notifyAt`, `notificationSent` 필드는 API 호환을 위해 남기지만 정시 발송에는 사용하지 않는다.

## 구현

기존 `NotificationScheduler`가 실행 시점을, `NotificationService`가 대상 조회·묶음·대표 항목 데이터 구성과 발송을 담당한다. 기존 `taskExecutor`에서 비동기로 보내며 FCM 호출 중 DB 트랜잭션을 유지하지 않는다. 기기 하나의 실패는 로그를 남기고 나머지 발송을 계속한다.

발송 전 `(기기, 알림 종류, 기준일, 그룹 키)` 슬롯을 `notification_deliveries`에서 원자적으로 선점한다. 오전 개별 알림은 할 일 ID를 그룹 키로, 저녁 묶음은 고정 그룹 키를 사용한다. 성공한 슬롯은 다시 발송하지 않고, 실패한 슬롯은 즉시 해제한다. 처리 중 프로세스가 종료된 슬롯은 30분 뒤 다시 선점할 수 있다. 정시 실행 외에도 5분마다 가장 최근 오전/저녁 슬롯을 재확인해 서버 재시작이나 일시 장애로 놓친 실행을 보완한다.

게시판은 기존의 전역 최초 수신 및 제보 기기 한 대 발송 정책을 유지한다. 기존처럼 요청의 FCM 토큰을 이벤트에 전달한다. 게시판 기록이 커밋된 뒤 사용자 알림 설정과 해당 토큰의 등록 여부를 다시 확인하고, 요청 토큰으로 발송한다. 수강생 전체에게 보내는 기능은 아니다. 첫 제보자가 OFF이면 게시판은 기록하되 알림은 보내지 않는다.

게시판 제목은 기존 `title` 필드로 전달하며 표시용 알림 제목이 아니다.

## 앱 연동

기존 `sendSilentPush()`로 FCM data만 보낸다. 서버는 표시용 제목·본문과 이동 경로를 만들지 않는다. 앱이 알림 종류, 항목 수와 대표 항목 정보로 문구와 탭 이동을 결정한다. 모든 data 값은 문자열이다.

| data | 값 |
| --- | --- |
| type | dueToday / deadlineApproaching / newTodo / newBoard |
| count | 할 일 알림의 항목 수. 1이면 상세, 2 이상이면 홈으로 이동 |
| representative_todo_id | 마감 시각, Todo ID 오름차순으로 고른 대표 할 일 ID |
| todo_title | 대표 할 일의 원본 제목 |
| todo_id | 단일 할 일에만 포함하는 실제 Todo ID. 기존 필드 유지 |
| todo_type | 대표 할 일의 ASSIGNMENT / QUIZ / COMMONS |
| subject_name | 대표 할 일의 과목명. 없거나 공백이면 생략 |
| due_date | 대표 할 일의 한국 로컬 마감 시각(ISO LocalDateTime) |
| action | 단일 마감 알림에만 기존 deadline_approaching 유지 |
| title | 게시판 알림에만 포함하는 기존 게시판 제목 |

앱은 `type`별로 기획된 제목·본문을 구성한다. 할 일 유형을 과제/퀴즈/강의로 표시하고, 묶음은 대표 항목과 `count - 1`건으로 표시한다. 과목명 누락 시 대체 문구도 앱이 정한다. 게시판에는 할 일 ID가 없으므로 홈으로 이동한다.

기존 단일 마감·게시판 식별 필드는 유지하지만 신규 종류와 묶음 처리는 앱 수정이 필요하다. 앱은 한 메시지에 대해 새 type 처리와 기존 action 처리를 중복 실행하지 않아야 한다. 새 데이터 규약을 지원하는 앱을 먼저 배포한다.

## 운영 전제

DB 선점으로 여러 서버나 동일 작업 재호출에 의한 중복 발송을 막는다. 단, FCM이 메시지를 수락한 직후 완료 상태 저장 전에 프로세스가 종료되는 경우에는 외부 시스템과 DB를 하나의 트랜잭션으로 묶을 수 없어 재시도 시 중복될 수 있다. 가장 최근 정시 슬롯은 5분마다 재시도하지만 그보다 오래된 알림을 무기한 소급 발송하지는 않는다. FCM 수신 시각은 네트워크와 OS에 따라 지연될 수 있다.

조회용 인덱스 `todo(due_date)`, `user_todo_status(created_at,is_completed)`가 추가된다. 운영에서 자동 DDL을 사용하지 않으면 배포 전에 반영한다. `createdAt`의 의미가 바뀌지 않도록 JVM 기본 시간대를 배포 간 동일하게 유지한다.
